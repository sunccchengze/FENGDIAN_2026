## 硬性规则

1. **规范先行**：文件结构、命名、数据格式以 `CLAUDE.md` 第五节/第六节 + `README.md` 为准。改规范先改文档，再改实践。
2. **按改动范围验证**：实现正确性运行受影响模块的测试或最小复现，算法性能结论运行对应实验；文档修改检查内容、链接和格式。保留可复现的验证结果；通过后仅在新改动或新证据需要时扩大或重复验证。不注释报错绕过，找根本原因。
3. **git 隔离**：实际修改任务使用 Git 管理，每个任务形成原子提交；只读任务不创建分支或提交。完整流程见 `GIT_WORKFLOW.md`。
4. **实验管理**：超参和结果记表（markdown/CSV），每次实验在 `optimization_control/experiments/YYYYMMDD_简短描述/` 下留 `config.yaml` + `metrics.csv` + `summary.txt`。
5. **随机种子**：全局统一 `seed=42`，写进每个 config。
6. **密钥不进代码**：token、密钥放环境变量，不写进代码/commit/日志。
7. **大文件不进 git**：>100MB 数据、模型放 `data/`、`experiments/`（已在 `.gitignore`）。
8. **不越界**：不做仿真组/PINN 组/可视化组的活；需要队友交付物时明确格式与时间要求。

## 本地 Git 管理

1. 三层边界：本地文件目录用于工作，暂存区只放当前任务，本地仓库保存验证通过的提交；不得直接编辑 `.git/`。
2. 稳定分支：`master` 只接收验证通过的状态；Codex 实际修改任务使用 `codex/<task>` 分支。开始时记录已有改动，只处理本任务文件，不要求清理其他任务状态。
3. 精确暂存：使用 `git add -- <明确文件列表>`，默认禁止 `git add .`。
4. 提交前检查：必须查看 `git diff --cached` 并运行 `git diff --cached --check`；验证失败不得提交。
5. 本地闭环：任务提交后能够安全快进时使用 `git merge --ff-only` 合并到 `master`；否则保留已验证提交并报告阻塞，不为收尾改动其他任务。默认仅使用本地仓库；用户明确指定远程仓库并授权上传时，按 `GIT_WORKFLOW.md` 的授权交付约定执行，不重复请示。
6. 状态入口：运行 `tools/project_git_status.ps1` 查看工作区、暂存区和本地仓库状态。

## 工作流（PPO 项目）
1. 技术栈：算法改进用 cleanrl 的 PPO 单文件起步；应用落地用 stable-baselines3
2. 任务边界：不同独立目标分任务；同一目标所需的实现、验证和修复在当前任务内完成。用户要求时另开任务；确需隔离上下文时说明理由并由用户决定，不以搭环境、baseline、改进点的阶段划分强制交接。
3. 迭代循环：改超参/算法变体 → 跑训练 → 看日志（tensorboard/wandb）→ 分析再改
4. 结题输出：实验汇总表、对比图、报告章节由我起草
