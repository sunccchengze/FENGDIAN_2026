**项目名称**：融合数据-物理驱动的风电流场感知与智能调控研究

**核心目标**：开发风电场实时功率智能控制系统，通过"感知→建模→优化→验证"路径，实现风机功率的精准协同调控。最终交付一套多机协同智能功率控制数字孪生演示平台。

5. 基于偏航协同的风电场多机功率分配（MADDPG 多智能体）
6. 系统集成与虚实闭环验证（数字孪生 + 3×3 微型风机阵列）

## 3. 学习指南：优化控制从零理解

> 本章为新手入门而写。如果你是 Claude Code（AI），在协助小红写代码时，遇到需要解释的概念，优先参考本章的类比和表述方式。

### 3.1 什么是"优化控制"

**控制** = 通过调整"旋钮"，让一个系统按你的意愿运行。

**优化** = 达到目的的方法不止一种，要找最好的那种。

以开车类比——你从 A 开到 B，踩油门就能到，但你还要考虑：
- 油耗尽量低（经济性）
- 不能超速（安全约束）
- 路上有别的车（外部干扰）
- 到达时间有要求（调度指令）

优化控制就是**算出什么时候踩多深的油门、什么时候打多大的方向盘**，让所有目标同时达到最优。

在风电里，风机的"旋钮"有三个：

| 控制量 | 物理含义 | 调整速度 | 影响 |
|--------|----------|----------|------|
| **桨距角** (pitch angle) | 叶片绕自身轴旋转，改变迎风角度 | 秒级 | 直接影响捕获功率量 |
| **转速** (rotor speed) | 叶轮旋转快慢 | 秒级 | 影响功率和机械载荷 |
| **偏航角** (yaw angle) | 机舱水平转向，改变朝向 | 分钟级 | 影响尾流方向，间接影响下游风机 |

项目核心目标：**电网说"我要 10MW"，风场就精准输出 10MW，同时各风机之间不能互相坑（尾流效应）。**

### 3.2 为什么传统 PID 不够用

目前工业界风机控制主要靠 **PID 控制器**——根据"当前功率与目标功率的差值"按公式计算修正量。它的优点是简单可靠，但有三个致命局限：

1. **只能针对一个工作点调参**：风速 8m/s 调好的 PID 参数，到 12m/s 就不好使。风机运行范围很大（切入风速 3m/s 到切出风速 25m/s），一套参数走不了天下。
2. **处理不了多目标**：又要跟踪功率指令、又要减少叶片疲劳载荷、又要保护机组不过载——PID 本质上只能盯一个误差信号。多目标加权后往往哪个都没做好。
3. **处理不了风机之间的耦合**：上游风机一偏航，尾流方向变了，下游风机的来流条件完全不同。PID 各自管各自的，不知道隔壁风机在干什么。

- [机器学习算法在风能中的应用：综述]（文献目录第 3 篇，22 页）综述了 ML 替代传统控制方法的全链条应用趋势

### 3.3 强化学习为什么适合

**强化学习（RL）** 的核心思想很朴素：让一个智能体在环境中反复试错，做对了给奖励，做错了给惩罚，最终学会最优策略。

```
         ┌──────────────────────┐
         │   RL 控制器（智能体）  │
         │   输入：观测状态      │
         │   输出：控制动作      │
         └──────┬─────────┬─────┘
                │ 动作     │ 奖励
                ↓          ↑
         ┌──────────────────────┐
         │   环境（风机 + 流场）  │
         │   收到动作 → 物理响应 │
         │   返回新状态 + 奖励   │
         └──────────────────────┘
```

和 PID 的对比：

| | PID | 强化学习 |
|---|-----|----------|
| 如何处理非线性 | 只能线性近似 | 神经网络天然处理非线性 |
| 如何适应多工况 | 需要人工切换参数组（gain scheduling） | 从数据中自动学习跨工况策略 |
| 如何处理多风机耦合 | 各自独立，不管别人 | 多智能体共享信息，主动协同 |
| 如何改进 | 依赖工程师经验调参 | 数据驱动，跑的交互越多越好 |

- [夏普利值论文]（文献目录第 4 篇）分析各环境因素对风电功率影响的相对重要性——你设计奖励函数时可以参考，哪些因素权重应该更高

### 3.4 PPO：单台风机的"稳妥教练"

**PPO（Proximal Policy Optimization，近端策略优化）** 是目前最主流的深度 RL 算法之一。

直观理解（教练类比）：
> 一个教练在训练运动员。每次训练后，教练根据表现给出改进建议，但教练有一个原则——**每次改进步子不要迈太大**，防止练崩。PPO 的"近端"就是这个意思：新策略和旧策略不要差太多，用"clip"操作限制更新幅度。

适合你项目的原因：
- **连续动作空间**：桨距角和转速是连续值，PPO 原生支持
- **训练稳定**：相比 DDPG/TD3 等算法，PPO 不容易训练崩溃，对新手友好
- **Stable-Baselines3 有成熟实现**：GitHub 8k+ star，文档齐全，论文可直接引用

一句话总结 PPO 在做什么：**学习一个"从观测到动作"的映射，当观测到"功率偏低 + 风速够"时，输出"减小桨距角 + 提高转速"的概率最高。**

### 3.5 MADDPG：多台风机的"团队教练"

**MADDPG（Multi-Agent Deep Deterministic Policy Gradient，多智能体深度确定性策略梯度）** 是 PPO 的"多机扩展版"。

直观理解（篮球队类比）：
> 五个人打篮球。每个人自己决定怎么跑位、什么时候投篮（actor），但有一个教练从全局视角告诉每个人"你刚才那个选择对团队好不好"（critic）。训练久了，大家不用教练也能默契配合。训练时可以用全局信息，执行时各风机只看自己的局部观测。

你的项目用 MADDPG 解决的核心问题：
- 上游风机**主动偏航**把尾流甩到旁边 → 自己损失 <2% 功率
- 下游风机来流恢复 → 多收 >10% 功率
- 全场净收益：总发电量提升 5%-10%

这就是申报书说的"牺牲单机局部利益以保护下游机组"。

**第 1 步（现在就做）**：用解析公式近似单台风机

风机捕获功率由叶素-动量理论（BEM，你的申报书步骤三）给出：

```
P = 0.5 × ρ × A × Cp(λ, β) × V³
```

- `ρ`：空气密度（≈1.225 kg/m³）
- `A`：扫风面积（= πR²，R 是叶片半径）
- `Cp(λ, β)`：功率系数，由桨距角 `β` 和叶尖速比 `λ` 共同决定
- `V`：来流风速

`Cp` 可以用经验公式近似（不需要 CFD 数据）：
```
Cp(λ, β) = 0.5176 × (116/λi − 0.4β − 5) × e^(−21/λi) + 0.0068λ
其中 1/λi = 1/(λ + 0.08β) − 0.035/(β³ + 1)
```

再加上一阶转速动力学：
```
J × dω/dt = Ta − Tg
Ta = 0.5 × ρ × A × R × Cp(λ, β) × V³ / ω    # 气动转矩
```

这就构成了你的第一个 RL 环境——不需要等仿真组、不需要等 PINN 组。

**第 2 步（PPO 训练）**：在简化环境上训练，对比 PID 基准。

**第 3 步（环境升级）**：等 PINN 组交付后，把解析公式替换为代理模型推理。

## 7. 开发流程

### 实验驱动开发

每轮迭代遵循：**假设 → 环境 → 算法 → 实验 → 记录 → 结论**

1. **假设**：明确这轮想验证什么（如"增加尾流惩罚项能降低下游功率损失"）
2. **环境**：如果需要新环境功能，先改环境，确保通过基本测试
3. **算法**：修改奖励函数/网络结构/超参数
4. **实验**：运行训练，记录指标
5. **记录**：在 `experiments/YYYYMMDD_简短描述/` 下保存：
   - `config.yaml` 超参数配置
   - `metrics.csv` 训练曲线数据
   - `summary.txt` 假设、观察、结论（几行即可，不用长文）
6. **结论**：假设成立/不成立/需要更多实验

### 复现性底线

论文级别可复现要求，至少做到：
- 所有训练脚本的**随机种子固定**（`seed=42` 统一值，在 config 里声明）
- 训练配置和结果一一对应，不存在"跑完不知道参数是什么"的情况
- 用于论文图表的数据来自 `experiments/` 目录，不是临时跑的

### 实验追踪

用 **MLflow** 做实验管理：
- 自动记录超参数、metrics、模型 artifact
- 训练脚本启动时 `mlflow.start_run(run_name="简短描述")`
- 查看平台用 `mlflow ui` 启动本地 web 看板

## 8. 代码规范

原则：**命名清楚即可，不强求类型注解和 docstring。但关键地方必须说明。**

### 必须遵守
- 文件名用英文小写下划线：`simplified_turbine.py` 不是 `简化风机.py`
- 变量名要有意义：`pitch_angle` 不是 `pa`，`wind_speed` 不是 `ws`
- 自定义 Gymnasium 环境必须继承 `gym.Env`，实现 `reset()`, `step()`, `render()` 标准接口
- 每个 `.py` 文件头一行注释说明本文件的用途

### 关键函数加一行注释
```python
def compute_reward(power_output, power_target, action_smoothness):
    """奖励 = 功率跟踪误差惩罚 + 动作平滑项，两项加权求和"""
```

### 不强求
- type hints（想加可以加，不加也可以）
- 完整 docstring
- 为每项改动新增单元测试；但实现正确性需运行受影响模块的已有测试或最小复现，算法性能结论需对应实验。文档修改只检查内容、链接和格式；验证通过后仅在新改动或新证据需要时扩大或重复验证。
