## 一、这份文件记录什么

本文件把 2026-09-20 前完成的 GitHub 同类项目调研、技术取舍和后续执行原则正式固化下来。
后续实现、文档整理、自动化和仓库治理都必须以本文件为基线；如果方案发生变化，应新建一份决策记录并明确 supersede 本文件的哪一节，不直接悄悄改写历史结论。

本轮确认的总原则是：

> **把仓库建设成 GitHub-native 的五人科研协作与交付工作台，而不是立即引入完整 MLOps、数据库或自研管理后台。**

核心证据链：

> 研究问题 → Issue → 分支/PR → 代码与数据版本 → 可复现实验记录 → 证据卡 → 评审 → 材料引用 → Release/阶段快照

### 2.1 共享责任

- 所有人都可以提交 Issue、分支和 PR；
- 所有人都必须对自己提交的结果负责，不把“AI 生成”当作验证；
- 任何人都可以指出其他领域的口径冲突；
- 跨领域结论必须至少由主责人和一名非主责人共同审阅；
- 孙承泽负责仓库集成和最终材料，不替代其他成员对物理、数据和算法结论的专业确认；
- 领域责任人发生变化时，先更新本文件和 `CODEOWNERS`，再改变流程。

> 当前仓库只能确认 `@sunccchengze` 这一 GitHub 账号。其他四位成员的 GitHub handle 不在仓库历史中被可靠确认，因此不猜测账号、不把显示姓名直接写进 `CODEOWNERS`。在账号确认前，责任以本表和 PR 指定审阅人为准。

## 四、协作规则

### 4.1 主分支规则

- `main` 是可交付和可引用的稳定分支；
- 不直接向 `main` 推送实质修改；
- 每个工作从 Issue 开始，使用独立分支；
- PR 必须说明关联 Issue、变更范围、验证方式和证据位置；
- 普通代码/文档修改至少一名队友审阅；
- 数据口径、物理模型、关键数字、对外材料和发布至少两名队友审阅；
- PR 合并后关闭关联 Issue，并在 Issue 中留下结果摘要；
- 不使用 `final_v2`、`latest_new`、`really_final` 等文件名管理版本，使用 Git 历史、Tag、Release 和元数据。

建议分支前缀：

- `feat/`：新功能或新研究能力；
- `fix/`：Bug、死链、数据错误；
- `exp/`：实验、验证和数据分析；
- `docs/`：文档、决策和治理；
- `material/`：答辩、阶段总结和申报材料；
- `chore/`：构建、依赖和仓库卫生。

### 4.2 GitHub 对象如何分工

| GitHub 对象 | 只负责什么 | 不负责什么 |
|---|---|---|
| Issue | 任务、实验问题、决策请求、文献和证据登记 | 不代替仓库内最终记录 |
| PR | 具体修改、审阅、验证和合并 | 不作为长期唯一实验日志 |
| Project | 状态、负责人、优先级、里程碑和阻塞 | 不复制整篇研究结论 |
| Discussion | 开放讨论、文献交流、方案比较 | 重要结论必须回写文件或 ADR |
| Markdown 记录 | 可引用、可审阅、可版本化的事实 | 不记录重复且互相冲突的数字 |
| Release/Tag | 冻结的阶段或提交版本 | 不改变源文件事实 |

### 4.3 会议和外部工具

微信群、腾讯文档、HackMD、Google Slides 等可以用于即时协作，但以下内容必须回写仓库：

- 影响代码或数据的决定；
- 对申请书、物理口径或答辩数字的裁决；
- 会议中的任务分配；
- 外部材料的最终版本和来源；
- 需要以后复核的失败尝试。

## 五、证据记录标准

每个重要结论至少应能回答：

1. 研究问题或假设是什么？
2. 输入数据从哪里来，哪个版本？
3. 使用了哪个代码 commit？
4. 使用了什么环境和命令？
5. 结果是什么，是否成功？
6. 是否存在失败尝试、适用域或限制？
7. 谁审阅了它？
8. 哪些材料或页面引用了它？

证据记录使用 `docs/templates/证据卡模板.md`。新建证据时，应优先拥有唯一编号，并链接到对应 Issue、PR、代码、数据 manifest 和最终材料。

当前已确认的权威入口包括：

- 申请书和交付物边界：`docs/03_申请书一致性审计报告.md`；
- 综合评审和验收：`docs/08_合并评审_最终清单.md`；
- 两仓迁入台账：`docs/12_两仓归一_wind_farm_viz迁入与分支清理.md`；
- 三风机改造决议：`docs/13_0919组会决议_三风机改造方案与3x3留档.md`；
- `twin` 运行、口径和实测：`twin/README.md`；
- `viz` 封板数据、契约和复现：`viz/README.md`、`viz/FREEZE.md`；
- 对外材料数字口径：`materials/README.md`。

## 六、数据和大文件策略

### 6.1 默认进入 Git 的内容

- Markdown、YAML、JSON、CSV 等可审阅文本；
- 源代码和测试；
- 小型、必要且有来源的图像；
- 已冻结、确实需要随交付物保存的 PDF/PPTX/DOCX；
- 生成文件的说明和 manifest。

### 6.2 默认不直接进入 Git 的内容

- 无法说明来源的大型原始数据；
- 可由脚本重新生成的大量中间产物；
- 本地缓存、环境、临时截图和未审阅视频；
- 私有、敏感或违反授权的数据。

外置数据必须登记来源、日期、权限、大小、SHA-256、获取方法和对应代码版本。当前仓库的约 66 MiB PSD 作为已有历史资产保留，但新增大文件必须先经过审阅。

### 6.3 DVC/Kedro 的升级条件

MVP 不引入 DVC 或 Kedro。只有当数据版本、模型版本、实验数量或稳定流水线真正超过 Git + manifest + 脚本约定的承载能力时，才单独新建 ADR 评估升级。

## 七、技术选型结论

| 领域 | 当前采用 | 暂不采用 |
|---|---|---|
| 任务与讨论 | GitHub Issues / Projects / Discussions | Jira、Notion 作为唯一事实来源 |
| 文档与证据 | Markdown + Git + Issue/PR 链接 | 立即建立数据库 |
| 运行和验证 | 现有 `npm run verify`、Python 脚本和 requirements | 全仓强制 Docker/Kedro |
| 数据版本 | Git + manifest + SHA-256 | MVP 直接引入 DVC |
| 发布 | Tag + GitHub Release，必要时再接 Zenodo | 自研发布平台 |
| 外部展示 | 先打磨 README 和 Markdown 导航，稳定后再评估静态文档站 | 立即增加新的 Web 应用 |
| CI | 低权限仓库质量检查和现有 `twin` QA | 给 PR 工作流写权限 |

## 八、MVP 和验收标准

### MVP 必须完成

- 根 README 成为真正的项目入口；
- 五人分工和责任边界入库；
- `CONTRIBUTING.md`、Issue Forms、PR 模板完成；
- 形成实验、决策、会议、证据和材料模板；
- 建立本地仓库质量检查；
- 建立文档、证据和材料导航；
- 用一个真实任务完整跑通 Issue → PR → 证据 → 材料引用；
- 不破坏 `viz` 封板历史和 `twin` 已有验证链；
- 关键数字能够定位到权威来源。

### MVP 不做

- 不立即重构 `viz/`；
- 不批量重命名历史文档；
- 不引入 DVC、Kedro、数据库或自研后台；
- 不将所有外部工具一次性替换；
- 不把生成产物伪装成源文件；
- 不在没有真实 GitHub handle 的情况下猜测成员账号。

## 九、执行顺序

1. **治理基线**：本文件、贡献规则、模板、导航和本地质量检查；
2. **GitHub 控制面**：Labels、Project、分支保护和真实账号绑定；
3. **真实试运行**：选择一个研究或材料任务走完整闭环；
4. **高频文档整理**：根 README、平台 README、材料索引和权威数字；
5. **轻量自动化**：链接、空文件、大文件、质量门禁和 `twin` QA；
6. **按痛点升级**：只有真实需求证明必要时才评估 DVC、Kedro 或数据库；
7. **阶段发布**：Tag、Release、提交说明、证据清单和材料快照。
