# ADR-2026-001 · 采用 GitHub-native 轻量科研协作工作台

> 状态：已确认
> 日期：2026-09-20
> 提议人：孙承泽
> 审阅范围：五人项目组
> 关联方案：[`docs/14_协作治理与可复现研究工作台方案.md`](../14_协作治理与可复现研究工作台方案.md)

## 背景

`Dachuang-SZLS` 已经同时承载科研可视化、数字孪生、研究记录、迁移台账和对外材料。继续只依靠个人经验、聊天记录和最终代码，会导致任务覆盖、数据口径漂移、实验不可复现和答辩材料无法追溯。

团队规模为五人，当前真正的瓶颈是流程、证据和文档治理，而不是缺少一个新的服务端平台。

## 候选方案

### 方案 A：GitHub-native 轻量工作台

使用 Issues、Projects、Discussions、PR、Markdown、Actions、Tags 和 Release；数据先用 manifest/checksum 管理，DVC/Kedro 按需升级。

### 方案 B：立即引入 DVC/Kedro/数据库或自研后台

一次性建立数据版本、流水线、实验数据库和 Web 管理界面。

## 决策

选择方案 A。

当前执行组合为：

- GitHub Issues / Projects / Discussions / PR；
- `main` 保护和 PR 审阅；
- Markdown 研究记录和证据卡；
- Git + manifest + SHA-256 数据治理；
- 现有 `twin` 本地验证链；
- 低权限仓库质量 Action；
- Git Tag/Release 作为阶段快照。

当前不引入 DVC、Kedro、数据库、自研后台或独立 ELN 服务。

## 取舍理由

- 与现有仓库、历史和团队工作方式兼容；
- 不增加新的长期服务和凭据管理；
- 先解决“谁做、为什么做、如何验证、如何引用”；
- 可逐步升级，不需要一次性迁移 `viz/` 历史资产；
- GitHub PR、Issue 和 Git 历史能够直接留下协作痕迹；
- 对五人团队的学习和维护成本可控。

## 影响

- 所有实质修改应从 Issue 和分支开始；
- `main` 成为可交付稳定线；
- 关键数字进入证据卡并链接到材料；
- 新增大数据和模型必须先登记来源与存储方案；
- `viz/` 继续封板，`twin/` 继续现役迭代；
- 未来如果真实需求证明 Git 不足，再通过新的 ADR 评估 DVC/Kedro/数据库。

## 重新评估条件

当出现以下情况之一时，重新评估本决策：

- 多版本数据已经无法用 manifest 和 checksum 管理；
- 需要多人共享大规模数据缓存；
- 需要稳定、重复执行且依赖复杂的数据流水线；
- 需要正式审计时间戳、敏感数据权限或机构级 ELN；
- GitHub Project 无法表达跨项目资源和里程碑；
- 团队实际运行一个试点后发现当前流程无法被持续执行。
