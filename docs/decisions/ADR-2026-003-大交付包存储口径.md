# ADR-2026-003 · 大交付包的存储口径：git 收什么，Release 存什么

- **状态**：**已批准并生效**（2026-10-22，用户明确答复「1.01 GiB **存量不动，规则收紧**」，采纳 §3 全部五条）
- **生效日**：2026-10-22（门禁 `ci/repo_quality.py` 同日加了对应检查）
- **提出**：Arena Agent（仓库治理）\n- **批准**：用户（孙承泽），2026-10-22
- **影响范围**：`materials/**` 的交付包、`optimization_control/**` 的实验归档、今后所有队友交付
- **关联**：`docs/project/TIMELINE.md` §5 #1、#12；`materials/README.md` §7；分支吸收审计 §5

## 1. 背景：同一件事已经被判成两个相反的结论

| 交付包 | 体积 | 当时的处理 | 依据 |
|---|---|---|---|
| 厉今飞 PINN 三机模型（2026-10-03） | 603.8 MB 单文件 | **不入库**，等复现时再定 | 超 GitHub 单文件 100 MB 硬限 |
| 洪祖名优化控制完整交付（2026-10-07） | ≈1.01 GiB，拆成 58 卷（每卷 ≤80 MiB） | **已入库**（2026-10-21 吸收） | 每卷都低于 95 MiB 门禁线 |

两条都不算错，但**判法不同**：一个按「单文件」判，一个按「分卷后单文件」判。结果是同一个仓库里，
603.8 MB 被挡在门外，1.01 GiB 反而进来了。这就是 `TIMELINE` §5 #12 说「需一次性裁定」的原因。

**用户 2026-10-22 的提问**：「我不了解 [这件事]，你的判断是怎样的？」——本 ADR 就是回答。

## 2. 三个候选方案

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A · 分卷入 git**（现状） | 大包切成 ≤95 MiB 的卷提交 | 不依赖外部服务，clone 即得全量 | 体积**永久**写进每个 clone（`main` 已从 483 MB 涨到 1.59 GB）；每次改动都重传；`git log --follow`、diff、CI 全部变慢；一旦入库几乎不可能干净撤回 |
| **B · Git LFS** | 大文件走 LFS 指针 | git 历史里只有指针；`git lfs pull` 按需取 | 每个 clone 都要装并配置 LFS，队友漏配会拿到指针文件；免费额度 1 GB 存储 / 1 GB 月流量，一次 clone 就可能耗尽；迁移需要改写历史 |
| **C · Release 资产 + 仓库留清单** | 大二进制挂 GitHub Release（单文件上限 2 GB，不进 git 对象库），仓库里只放 `manifest.json` + `SHA256SUMS.txt` + 下载命令 | clone 体积不增长；URL 稳定、可长期引用、可按 tag 绑定；不需要任何人装额外工具 | 离线复现要先手动下一次；`ci/repo_quality.py` 无法离线校验资产，必须靠仓库里的 sha256 留证 |

## 3. 决策（建议）

**采用 C，并给出明确的分界：**

1. **进 git**：代码、配置、文档、Markdown、`manifest.json`、`SHA256SUMS.txt`、单文件 **≤50 MiB** 的图表与结果文件、
   以及任何「小到能解释清楚」的证据件。
2. **进 Release**：单文件 **>50 MiB** 的模型权重（`.keras`/`.pt`/`.h5`）、历史归档 zip、录屏、原始数据集。
   git 侧必须同时留下：资产文件名、字节数、sha256、Release tag、以及一行可直接执行的下载命令。
3. **分卷不再是入库的理由**：把 614.8 MB 切成 7 卷不改变「它是 614.8 MB 二进制」这个事实，只绕过了单文件限制。
4. **存量不动**：已入库的 ≈1.01 GiB（`materials/洪祖名/20261007_optimization_handoff/archives/`）**保持现状，不改写历史**——
   改写要 force-push 全部协作分支，风险远大于收益。分歧只从本 ADR 生效日起按新口径判。
5. **门禁补一条**：`ci/repo_quality.py` 已有 50 MiB 告警 / 95 MiB 错误；建议再加一条 **warning 级**
   「`materials/**` 下新增 >50 MiB 文件必须在同目录 `SHA256SUMS.txt` 里有条目且指向 Release 资产」。

## 4. 理由（为什么不选 A / B）

- **A 的代价是不可逆的**。git 的对象一旦被 clone 出去就收不回来；本仓已经踩过一次（335 个提交被甩掉后靠 `-s ours` 接回）。
  1.01 GiB 已经在那里了，再往上叠只会让「clone 一次」越来越痛，而收益只是「少点一次下载」。
- **B 对五人小队不划算**。LFS 要求每个成员本地配置；免费额度按**下载流量**算，一次全量 clone 就可能超。
  对一个只有两名成员频繁提交、其余成员主要看 Markdown 的仓库，这是负担而不是解决方案。
- **C 的风险可控**。唯一的软肋是「资产不在 git 里，删了就没」。可以用三条约束兜住：资产挂在**带 tag 的正式 Release**（不是草稿）；
  仓库里留 sha256 + 大小 + 文件名；每次收取都要能在 `materials/**/README.md` 里找到「去哪下、怎么校验」两句话。

## 5. 影响

- 新交付包的入库动作从「切分卷 + 提交」变成「传 Release + 提交清单」，**提交量下降一个数量级**；
- 复现多一步：先按 `README` 里的命令下资产并 `sha256sum -c`，再解包。这一步**必须写进 README**，否则复现者会以为仓库缺件；
- 私有仓库的 Release 资产同样只对协作者可见，不影响保密性；
- `docs/evidence/` 的证据卡今后引用大文件时，链接指向 Release 资产 URL + 仓库内 sha256，而不指向 git 路径。

## 6. 验证方式

- 本次 2026-10-22 的两份交付（163.3 MB + 614.8 MB + 26.9 KB 截图）作为**第一个试点**：
  614.8 MB 的 PINN 整包挂 Release，仓库只收解包后的代码/配置/清单；
- 试点跑完，在 `materials/README.md` §7 把「存储方式待裁定」两行改为「按 ADR-2026-003 执行」；
- 若试点证明「复现者拿不到资产」（例如 Release 资产失效、或协作者无权限），则本 ADR 退回重审，改走 B。

**门禁实测**：临时放一个 51 MiB 文件（`git add -N`）→ 两条 warning 如期出现；删除后回到 **0 error / 0 warning**。
基线文件不再刷屏——这不是「放行」，是「已登记的历史，不再重复提醒」；新增文件一律按新规判。

**对 2026-10-22 这次交付的适用**：`三机优化控制与中期答辩交付_20261022.zip`（163.3 MB）与
`PINNs_multi_turbine_wake_simulation-outputchange(1).zip`（614.8 MB）**都不进 git**，走 Release 资产；
仓库只收解包后的代码、配置、文档、清单与 sha256。

## 9. 一个必须写下来的教训：Release 资产不等于「机器可读」

2026-10-22 提出本 ADR 时，我（Agent）默认「挂到 Release 就能被取用」。实测不成立：

| 目标域名 | 结果 |
|---|---|
| `github.com` / `codeload.github.com` / `api.github.com` | 可达 |
| `release-assets.githubusercontent.com`（Release 资产的真实下载地址） | **不可达**（TLS 握手失败） |
| `raw.githubusercontent.com` / `media.githubusercontent.com` | **不可达** |

也就是说：**Release 资产是「给人用的长期仓库」**（浏览器、`gh release download`、团队都能取），
但对本仓库的 Agent 沙箱**不是取件通道**。Agent 要拿到字节，只能走 **git 本身**（提交进分支）。

这条不影响本 ADR 的结论——存储口径解决的是「会不会永久撑大 clone」，不是「Agent 怎么取件」；
但它必须写在这里，否则下一个接手的人会重复我这次的错误判断。
