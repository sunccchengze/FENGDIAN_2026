## 2. 候选方案

### 方案 A：维持 2026-09-20 治理表，只在 `materials/README.md` 加提醒

优点：不动已确认文档。缺点：三份治理文档与申请书、成员自述、答辩材料长期打架；PR 模板「基线数据 / 数据口径」勾选后找不到正确审阅人。

### 方案 B：以申请书封面与成员自述为准，新建 ADR 修订三份文档

优点：与法定申报文件和成员自我认定一致，答辩材料不需要再解释两套分工。缺点：需按 `docs/14` 的变更流程新建决策记录并改三处。

## 3. 决策

选择方案 B。用户 2026-09-21 裁定：「以申请书封面和两人自述为准」。修订后的分工表：

| 成员 | 职责 | 主要仓库责任 | 必须审阅的内容 |
|---|---|---|---|
| **厉今飞** | **项目负责人**、AI 模块负责人 | 功率 / 流场预测神经网络、PINN、POD 降阶与轻量化路线、训练与评价方案、各模块目标与接口对接、总体进度 | 模型结构与训练结论、预测精度数字、AI 路线取舍、跨模块接口、结题范围 |
| **袁夫达** | 建模负责人 | 风机选型（NREL 5MW）、FLORIS GCH/CC 数据生成、数据字典 / 工况清单 / 来源与版本、FLORIS 与 Fluent 原理梳理 | 训练数据、基线工况与数据口径、单位/量纲、尾流模型假设与适用范围 |
| **田铭雨** | 仿真负责人（Fluent CFD） | CFD 算例、网格与湍流模型设置、边界条件、CFD 结果导出与质量证据、物理边界 | CFD 数据、物理假设、风场/尾流结论 |

不改变的部分：共享文件仍通过 PR 协作；跨领域结论仍需主责人 + 至少一名非主责人共同审阅；`CODEOWNERS` 仍只登记已验证的 `@sunccchengze`。

## 4. 取舍理由

- 申请书是立项的法定文件，封面「项目负责人 厉今飞」不是可以由仓库文档改写的事实；
- 「基线数据与数据口径」在实际工作中由生成数据的建模负责人（袁夫达）承担：数据格式、列定义、工况覆盖、GCH/CC 差异都写在他的两份文档里；
- 「降阶与代理模型」在实际工作中是 AI 模块的一部分：厉今飞的自述写明「代理模型代码准备与复现探索」「POD 降阶与小型神经网络结合的可行性」；洪祖名做的 XGBoost 代理模型优化保留在优化控制行；
- 2026-09-20 表是治理方案起草时的推断，没有一手材料支撑。
