## 0. 先读这段：为什么之前时间线读起来是乱的

### 0.1 本文件只管「什么时候发生了什么」，不管「事实是什么」

时间线是**导航层**，不是事实来源。任何数字、结论、口径都必须点进右列的原始记录去读，不要从本文件的摘要里引用。这条与 [`../README.md`](../README.md) §「文件质量标准」和 [`../../materials/README.md`](../../materials/README.md) 开头的「材料不是数字事实的第一来源」一致。

### 0.2 有两条互相错位的时间轴，混读必然乱

本项目的时间线**不是一条轴，是两条**：

| 轴 | 含义 | 例子 | 权威来源 |
|---|---|---|---|
| **事件日期** | 事情真实发生的那天：开会、微信群里发包、导师答复、模型打包 | 袁夫达的 FLORIS 数据包是 **2026-08-08** 发的 | 群聊截图 / docx 自述日期 |
| **入库日期** | 该文件的字节进入本仓 git 的那天 | 同一批交付件直到 **2026-09-21** 才 `git mv` 进 `materials/` | `git log --follow` |

两者最多相差 **5 个月**（申请书 2026-03-27 申报 → 现存件 2026-09-21 归位）。**下表的「日期」列一律是事件日期**；入库日期只在 §3 单独列，因为只有它才能解释「为什么某段时间 git 里没有动静但项目其实在推进」。

### 0.3 本仓有两个 `Initial commit`，git 起点 ≠ 项目起点

这是最容易踩的坑：

| 提交 | 日期 | 是什么 |
|---|---|---|
| `9dc5e2e` | 2026-07-28 | **前身仓库 `wind_farm_viz` 的 Initial commit**（科研可视化平台线） |
| `07038c6` | 2026-08-24 | **本仓自己的 Initial commit**（GitHub API `createdAt` = 2026-08-24T08:25:31Z） |

两条无关历史在 2026-09-19 由 `3c9603d`（`merge(repo): 并入 wind_farm_viz 全部历史与文件树 → viz/`）缝合，2026-09-21 又由 `31c3068` 把被 `66abeb5` 甩掉的 335 个提交用 `-s ours` 接回主线。

结果：

- 全仓 **353** 个提交里，**173 个早于本仓的创建日期**（2026-07-28 → 08-23，属 `wind_farm_viz` 线），**180 个**在建仓之后；
- `git log` 的第一页看到的不是项目起点；
- 项目真正的起点（**2026-03 申报、2026-05-17 首次组会**）**完全不在 git 历史里**——那时候还没有任何仓库。

所以判断「某件事什么时候发生」，**不能只看 git log**。

`wind_farm_viz`（前身，2026-07-28 → 09-14，已由用户删除）→ 本仓 `0824-2026` → `Dachuang-SZLS` → **`FENGDIAN_2026`（现名）**。

## 6. 维护规则

1. **新事件先进本文件**，再在分区明细里展开。本文件每行必须能点进一个原始记录；无法链接的事件要写明「无仓库材料」。
2. **只写日期、事件、类别、链接**，不复制数字。数字一律留在原始记录与 [`../evidence/`](../evidence/README.md)。
3. **区分事件日期与入库日期**（§0.2）。本文件主表用事件日期；只有滞后本身是话题时才进 §3。
4. **阶段可以追加，不要重排既有阶段编号**。阶段 5 之后新增写「阶段 6 · …」。
5. **§5 的缺口修掉一项就划掉一项**，并注明修复提交与日期；不要静默删除，否则读者无法知道它曾经存在。
6. 本文件改动**不需要**动 `ci/repo_quality.py` 的门禁范围，但如果新增了链接，请跑一次 `python3 ci/repo_quality.py` 确认 0 error。
7. **本文件不记待办**。「接下来谁干什么、卡在哪、哪天到期」的唯一来源是 [`WORKLIST.md`](WORKLIST.md)；本文件只在 §5 记「已知缺口」（即**事实层面**的缺失），两者互链不复制。
