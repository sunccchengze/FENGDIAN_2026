## 3. 时间线为什么读起来乱：三条结构性原因

### 3.1 有两条互相错位的时间轴

材料有**事件日期**（微信里发的那天、开会那天、打包那天）和**入库日期**（字节进 git 的那天），两者最多相差约 6 个月：

- 大创申请书：事件 2026-03-27 → 归位入库 2026-09-21；
- 三份 2026-08-08 交付件：事件 08-08 → 按人归档 2026-09-21（此前埋在 `viz/_archive/*/20260808/`，每份重复 2–4 次）；
- 17 张群聊截图：事件 07-26 → 09-20 → 入库 09-21。

既有文档里这两个日期**混在同一列**（如 `materials/集体/README.md` 的「日期」列既有申报日也有归档说明），读者无法判断哪个是哪个。本轮在主干里把两者**分成两张表**：§2 主表一律事件日期，§3 专门列滞后对照。

### 3.2 本仓有两个 `Initial commit`，git 起点 ≠ 项目起点

| 提交 | 日期 | 归属 |
|---|---|---|
| `9dc5e2e` | 2026-07-28 | 前身仓库 `wind_farm_viz` |
| `07038c6` | 2026-08-24 | 本仓（GitHub API `createdAt` = 2026-08-24T08:25:31Z） |

353 个提交中 **173 个早于本仓的创建日期**（2026-07-28 → 08-23），2026-09-19 由 `3c9603d` 缝合，2026-09-21 由 `31c3068` 用 `-s ours` 把被 `66abeb5` 甩掉的 335 个提交接回。

后果：`git log` 第一页不是项目起点；而项目真正的起点（2026-03 申报、2026-05-17 首次组会）**根本不在 git 历史里**。仓库名还换过三次（`0824-2026` → `Dachuang-SZLS` → `FENGDIAN_2026`），旧文档里的 `sunccchengze/Dachuang-SZLS` 链接靠 GitHub 重定向才没变成死链。

### 3.3 时间线有 6 条，没有主干

整理前，「某件事什么时候发生」需要翻 6 个地方，且彼此不互链：

| 分区 | 覆盖 | 整理前的状态 |

| `docs/meetings/README.md` | 会议入口表 5 行 | 与上一条部分重叠，无互链 |

| `docs/research/roundNN_*.md` | R11–R40 | 22 份文件，编号缺 11 个，无索引表 |
| `docs/12` + `docs/audits/` | 仓库治理 | 只覆盖 09-19 → 09-21 |
