## 6. 真正让 clone 变小：历史重写（只在 A/B/C 做完后做）

**事实**：删除工作树文件后，`.git` 仍保有全部历史对象，clone 体积**一点都不会降**。

### 6.1 方案

```bash
# 0) 前提：所有协作分支已合并；全员停止推送；已备份
git clone --mirror https://github.com/sunccchengze/FENGDIAN_2026.git backup.git

# 1) 用 filter-repo 删掉大路径（不可逆，但 backup 在）
pip install git-filter-repo
git filter-repo --force \
  --path materials/洪祖名/20261007_optimization_handoff/archives --invert-paths \
  --path docs/research/shots --invert-paths \
  --path materials/孙承泽/PS科研制图 --invert-paths \
  --path docs/research/mockups --invert-paths \
  --path docs/research/img --invert-paths \
  --path docs/screenshots --invert-paths \
  --path skills --invert-paths

# 2) 清垃圾、看结果
git reflog expire --expire=now --all && git gc --prune=now --aggressive
git count-objects -vH     # 目标：pack < 300 MB

# 3) 推回（所有提交哈希都会变）
git remote add origin https://github.com/sunccchengze/FENGDIAN_2026.git
git push --force --all && git push --force --tags
```

### 6.2 代价（必须提前接受）

1. **所有提交哈希改变**，`TIMELINE` 里引用的 40+ 个短哈希（`07038c6`、`f2a6f4f`、`66abeb5`…）全部失效；
2. tag `archive-main-before-2026-10-24-rewrite`、`twin-3x3-archive-20260919` 需要重建；
3. **五个人的本地 clone 全部作废**，必须重新 clone（不能 pull）；
4. 已开/已关的 PR 会变成「找不到提交」；
5. `git log --follow` 断代。

### 6.3 更稳的替代：开新仓

> 建一个干净的新仓（`FENGDIAN_2026_v2`），把当前树**作为首个提交**推上去，旧仓设为 archived 只读。
> 优点：不动历史、不可逆风险为零、clone 直接 0.36 GB；
> 缺点：丢历史（但历史已被 `HISTORY.md` + tag + Release 摘要承接）。

**我的建议**：选 6.3。理由：这是五人小队的过程仓，历史的价值远低于「今天能不能顺利 clone」。
